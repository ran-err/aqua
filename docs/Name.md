# Name 系统设计文档

## 1. 背景与目标

引擎中大量子系统需要用字符串标识实体（资产路径、组件类型名、属性名等）。直接使用 `std::string` 存在两个问题：

- **比较开销**：字符串比较是 O(n)，在反射查找、序列化匹配等高频路径上不可接受
- **内存冗余**：同一名称在不同对象中重复存储

Name 系统通过字符串驻留（string interning）将字符串映射为 `uint32_t`，实现 O(1) 比较和去重存储。

**不解决的问题**：本地化显示名、运行时字符串拼接、带格式的路径解析。

## 2. 设计

### 2.1 当前方案概述

两个类，职责分离：

| 类 | 职责 |
|---|---|
| `Name` | 值类型，持有 `uint32_t id_`，提供比较、转字符串等接口 |
| `NameRegistry` | 全局注册表，维护 `string ↔ id` 的双向映射 |

**核心流程**：

```
Name("Player")
  → NameRegistry::GetOrAdd("Player")
    → lookup_ 中查找
      → 命中：返回已有 id
      → 未命中：分配新 id = strings_.size()，存入两张表
  → id_ = 返回的 id
```

**数据结构**：

- `strings_`（`vector<string>`）：id → string，按分配顺序存储
- `lookup_`（`unordered_map<string, uint32_t>`）：string → id，用于去重
- id `0` 保留给空字符串，`Name()` 默认构造即为 None

**对外接口**：

- `Name(string_view)` — 构造并注册
- `Id()` / `IsNone()` / `ToString()` — 查询
- `operator<=>` — 按 id 比较，O(1)

### 2.2 设计理由

- **值语义**：`Name` 只有一个 `uint32_t`，可以自由拷贝、放进容器、作为 map key，零额外开销
- **Meyer's singleton**：`NameRegistry::Instance()` 用局部静态变量实现，避免静态初始化顺序问题，当前阶段最简单
- **只增不删**：Name 在引擎中通常是全局生命周期（类型名、属性名），不需要释放机制
- **接口最小化**：只暴露必要操作，内部实现可以自由替换

## 3. 备选方案与取舍

**编译期哈希（constexpr hash）**

不需要注册表，直接在编译期把字符串哈希为整数。优点是无运行时开销、无全局状态。缺点是无法从 id 反查字符串（调试困难），且哈希冲突只能靠概率保证。在需要序列化/调试输出名称的场景下不实用。

**`std::string` 直接比较**

最简单，不需要额外系统。但 O(n) 比较在反射属性查找等热路径上会成为瓶颈。UE、Godot 都选择了 interning 方案，说明这个开销在引擎规模下是真实存在的。

**第三方库（如 entt::hashed_string）**

成熟可靠，但引入外部依赖。作为引擎基础设施，Name 系统足够简单，自己实现可控性更好，也方便后续按需定制。

## 4. 约束

### 4.1 前提与风险

| 假设 | 被打破时的后果 |
|---|---|
| 单线程访问 | 多线程并发 `GetOrAdd` 会导致数据竞争 |
| Name 总量有限 | `uint32_t` 上限 ~4B，实际中不会触及，但 `vector` 和 `unordered_map` 在极端数量下可能有性能问题 |
| Name 不需要释放 | 如果需要热重载/卸载插件，已注册的 Name 会泄漏 |
| 不需要跨进程共享 | id 在不同进程中不稳定（取决于注册顺序） |

### 4.2 为什么现在不解决

- **线程安全**：当前没有异步加载或多线程子系统，加锁是纯开销。等引入任务系统/资产异步加载时再加 `shared_mutex` 或分片锁
- **内存回收**：引擎中 Name 的典型用法是全局生命周期，与类型系统、反射绑定。只增不删是 UE FName 的同款策略
- **跨进程稳定性**：当前是单进程编辑器，不涉及网络同步或多进程架构

## 5. 验证

- `ResetForTesting()` 允许测试间隔离注册表状态
- 需要覆盖的测试用例：
  - 相同字符串 → 相同 id
  - 不同字符串 → 不同 id
  - 默认构造的 Name `IsNone() == true`
  - `ToString()` 能还原原始字符串
  - 空字符串的 id 为 0

## 6. 未来演进方向

| 触发条件 | 演进方式 |
|---|---|
| 引入多线程资产加载 | 给 `NameRegistry` 加 `shared_mutex`，或按哈希分片降低锁竞争 |
| 需要编辑器/Runtime 隔离 | 将 singleton 替换为 context-based 注入，不同上下文持有独立 registry |
| 大量同名实体（如关卡中的 Actor） | 参考 UE FName 的 number suffix 机制（`Actor_0`, `Actor_1`） |
| 序列化/网络同步需要稳定 id | 引入确定性哈希或持久化映射表，使 id 不依赖注册顺序 |

当前接口（`Name` 只暴露 `Id()`/`ToString()`/比较）不会因上述演进而改变，内部实现可以自由替换。
