# 设计文档推荐结构

## 1. 背景与目标

这个功能解决什么问题？如果是基础设施，还要回答服务于什么上层需求？

需要说明：

- 用户/系统遇到了什么痛点
- 为什么需要这个功能
- 成功标准是什么
- 不解决哪些问题

## 2 设计

### 2.1 当前方案概述

这个功能是怎么做的？

需要说明：

- 核心流程
- 关键模块/类/函数的职责
- 数据如何流动
- 重要的状态变化
- 对外暴露的接口

### 2.2 设计理由

为什么这么做？

可以从这些角度回答：

- 简单性
- 可维护性
- 性能
- 可测试性
- 与现有系统的兼容性
- 团队/项目当前阶段的约束
- 实现成本

## 3 备选方案与取舍

还有什么方案？为什么不那么做？

可以比较：

- 更简单但扩展性差的方案
- 更通用但复杂度高的方案
- 性能更好但实现成本高的方案
- 更标准但不适合当前项目规模的方案
- 依赖第三方库/服务的方案
- 重构现有系统的方案

每个方案可以按这个格式写：

- 方案是什么
- 优点
- 缺点
- 为什么最终没有选择

## 4. 约束

### 4.1 前提与风险

这个实现依赖哪些假设？这些假设被打破会怎样？

可以考虑：

- 是否假设单线程/同步执行
- 是否假设数据量较小
- 是否假设输入格式合法
- 是否假设网络/文件/数据库稳定
- 是否假设调用顺序固定
- 是否假设某些状态不会被外部修改
- 是否假设某些操作不会失败
- 是否存在复制、缓存、共享引用带来的问题
- 是否有性能、并发、安全、兼容性风险

### 4.2 为什么现在不解决这些风险

这些风险为什么目前可以接受？

可以说明：

- 当前数据规模还小
- 当前没有并发场景
- 当前只是 MVP/课程项目/个人项目阶段
- 修复成本高于收益
- 有监控、测试或边界检查兜底
- 后续扩展时再处理会更合适
- 先保持实现简单，避免过早设计

## 5. 验证

我怎么知道它真的能工作？

可以写：

- 哪些测试覆盖它
- 哪些不变式会被 assert
- 如何监控
- 如何 debug
- 如何观察性能

## 6. 未来演进方式

当规模、使用方式或约束发生变化时，现有设计的哪些部分保持稳定，哪些部分可以替换，系统如何在不中断现有用法的情况下迁移？

需要说明：

- 哪些部分可以复用
- 哪些接口已经预留
- 哪些地方可能需要重构
- 添加新功能的大致步骤
- 当前设计是否会限制未来扩展
- 如果规模变大，可能需要怎样演进
